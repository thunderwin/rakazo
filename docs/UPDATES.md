# 更新与版本策略

> 状态：签名 Client Manifest 和静默配置同步已实现；runtime/Electron 包更新尚未实现。
> 核实日期：2026-10-21。
>
> 目标：高频更新尽量不打扰用户；业务层能热更新，Electron/原生层才重启。

## 1. 分层原则

| 层 | V1 行为 | 是否需要重启 |
|---|---|---|
| prompt、bot 模板、模型列表、配置 | 服务器下发签名包，本地校验后立即生效 | 否 |
| Web UI 资源 | 版本化资源；下次页面加载或轻量 reload 使用新版本 | 否，最多刷新 renderer |
| 本地 Agent runtime（JS/TS） | 后台下载、签名校验，下次启动使用新版本 | V1 需要重启 App；后续可热切换 |
| SQLite 迁移 | 在数据库副本上执行，成功后原子切换 | 否 |
| 浏览器扩展 | Chrome/Edge 自身管理更新 | 可能需要扩展重载 |
| Electron / Chromium / 原生模块 | 下载后退出时安装，或下次启动安装 | 是 |

**V1 不承诺 Electron 本体无重启更新。** 这类更新需要替换二进制，做不到安全热替换。

## 2. V1 最小更新闭环

```text
启动
  -> 读取本地版本
  -> 后台检查 manifest
  -> 下载配置包 / runtime 包 / shell 更新
  -> 校验签名和 SHA-256
  -> 配置包立即激活
  -> runtime 包暂存，下次启动生效
  -> shell 更新在退出时安装
```

要求：

- 不阻塞启动和当前对话。
- 下载失败不打断使用；下次再试。
- 更新包损坏、签名错误或版本回退时拒绝激活。
- 保留上一版本，失败可回滚。
- 不在用户正在执行任务时强制退出。

## 3. 版本目录

即使 V1 暂时在下次启动生效，也建议使用版本目录，方便后续热切换：

```text
userData/
  versions/
    runtime-2026.10.20.1/
    web-2026.10.20.1/
    config-2026.10.20.1/
  current.json
  previous.json
  staging/
```

`current.json` 只记录已验证、可启动的版本。写入时使用临时文件 + 原子 rename。

## 4. Manifest

Client Manifest 使用 Ed25519 签名。客户端只信任内置/打包时注入的公钥，不应用缺签名、
签名错误或正文 hash 不匹配的内容。当前实现见 `docs/ADMIN.md`。

示例：

```json
{
  "channel": "stable",
  "runtimeVersion": "2026.10.20.1",
  "webVersion": "2026.10.20.1",
  "configVersion": "2026.10.20.1",
  "minShellVersion": "0.3.0",
  "runtime": {
    "url": "https://updates.example.com/runtime-2026.10.20.1.tar.zst",
    "sha256": "..."
  },
  "config": {
    "url": "https://updates.example.com/config-2026.10.20.1.json",
    "sha256": "..."
  },
  "signature": "..."
}
```

规则：

- 只允许 HTTPS。
- 禁用降级；`minShellVersion` 不满足时提示用户升级客户端。
- 同一版本重复下载要幂等。
- manifest 和包都要校验。
- 签名私钥只在发布流水线/密钥库中，不在客户端。

## 5. 配置和 prompt 热更新

这部分最适合高频更新，V1 应优先实现：

- bot 模板、prompt、模型目录、定价和功能开关使用签名配置包。
- 配置包下载后先校验，再写入本地版本目录。
- 新配置只影响之后创建的 bot 或新请求；不覆盖用户已经编辑的 instructions。
- 保留上一版配置，解析失败时回滚。
- 不需要重启 App。

## 6. Runtime 更新

V1：

- 下载到 `staging/`。
- 校验并做最小健康检查（例如加载模块、检查版本、检查本地 DB schema 兼容性）。
- 写入新的 `current.json`。
- 提示“更新将在下次启动生效”，不阻塞当前使用。

后续可升级为热切换：

1. 保持旧的 runtime 进程继续服务当前任务。
2. 启动新的 runtime 进程。
3. 新请求路由到新进程。
4. 旧任务结束后 drain 并关闭旧进程。
5. 失败时继续使用旧进程。

热切换要求 runtime 与 Electron 壳分离；V1 不把它作为阻塞项。

## 7. 数据库迁移

本地数据库是用户数据，迁移必须保守：

1. 复制当前 SQLite 到临时文件。
2. 在副本上执行迁移。
3. 校验 schema 和关键表。
4. 原子替换原文件。
5. 保留上一版本备份。
6. 迁移失败时保留旧数据库并回滚 runtime。

不要直接在唯一的数据库上执行不可逆迁移。

## 8. 发布和回滚

- 使用 `stable` / `beta` 两个 channel。
- 先对内部设备和小比例用户放量。
- 监控启动失败率、崩溃率、模型网关错误率和迁移失败率。
- 出现问题时停止新 manifest 发布，保留旧版本继续工作。
- 客户端保留 `previous.json`，启动失败时自动回退。
- 服务端保留旧版本下载地址，不立即删除。

## 9. 安全红线

- 不执行未签名的远程 JS/配置。
- 不从 HTTP 下载更新。
- 不允许降级到有漏洞的版本。
- 不把签名私钥、模型供应商 key 或设备 token 打进客户端。
- 不把对话正文写进更新日志或遥测。
- 更新失败不能破坏本地数据库。

## 10. 与当前代码的差距

当前 `apps/desktop/src/auto-update.ts` 已经能：

- 启动后延迟检查更新
- 后台下载
- 使用 `electron-updater`
- 安装时调用 `quitAndInstall()`

但它没有：

- 版本化 runtime 目录
- 签名 manifest
- 配置包热更新
- runtime 进程分离
- 数据库副本迁移
- 热切换和 drain

因此当前实现只能做到“后台下载，退出时安装”，不能做到真正的业务层热更新。

## 11. V1 验收

- prompt/模板更新后，不重启 App 即可生效。
- 下载失败或签名错误不影响当前使用。
- runtime 更新在下次启动生效，且失败可回滚。
- Electron 更新在退出时安装，不打断当前任务。
- 本地数据库迁移失败时仍能用旧版本启动。
- 用户看不到长篇更新日志，只看到必要的状态。
