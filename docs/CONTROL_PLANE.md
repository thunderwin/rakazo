# 个人终端与企业托管控制面

> 状态：架构决策，尚未实现。确认日期 2026-10-21。

## 1. 产品定位

产品以个人终端为核心，服务器只承担账号、计费、企业管理和配置分发。

```text
个人终端
  ├─ Agent 循环和工具执行
  ├─ 对话、群聊和本地数据
  ├─ 浏览器、文件和本地 workspace
  └─ 自动下载组织分配的预设

服务器
  ├─ 登录和个人账号
  ├─ 企业组织与企业成员
  ├─ 企业统一付款和模型额度
  ├─ bot、群、Knowledge、Skills、routines 分发
  └─ 错误、用量和审计元数据
```

核心原则：

> **服务器管理和分发，客户端执行。**

服务器不会运行 Agent 去操作用户电脑，也不保存员工私有对话和文件。

## 2. 用户模型

### 2.1 当前版本

- 一个账号就是一个个人终端。
- 一个账号最多绑定一个当前企业组织。
- 客户端不提供企业切换器，也没有企业 workspace 概念。
- 登录后，服务器直接返回账号是否属于某个企业。
- 属于企业时，客户端自动同步该企业分配的预设。
- 不属于企业时，客户端就是普通个人版。

客户端可以显示一个轻量标识：

```text
Managed by Example Company
```

它只是账号属性，不是需要用户理解和操作的复杂层级。

### 2.2 本地数据

本地数据库继续按 userId 隔离，不为每个企业建立独立工作空间。

企业托管内容在本地单独标记：

- `managedByOrganizationId`
- package id
- version
- assignment source

企业分配的 bot、群、Knowledge、Skills 和 routines 显示为只读/托管。用户自己的 bot、对话、Memory 和文件不受影响。

如果账号更换或退出企业：

- 停止同步旧企业内容。
- 禁用或删除旧企业的托管预设。
- 保留用户自己创建的数据。
- 不需要切换本地数据库。

### 2.3 一个账号加入多个企业

当前版本不支持一个账号同时绑定多个企业。后台仍然可以服务多个企业，但每个账号只有一个当前 organization。

这样可以避免：

- 企业切换器。
- 多套本地数据库。
- 跨企业 Memory 混淆。
- 多企业同时扣费。

如果以后确有多企业需求，再单独设计账号切换。

## 3. 企业组织

服务器端仍按多租户建模，支持很多企业，但单个终端只看自己的当前组织。

```text
Organization
  ├─ Members
  ├─ Billing account
  ├─ Assigned bot templates
  ├─ Assigned group presets
  ├─ Assigned Knowledge
  ├─ Assigned Skills
  ├─ Assigned routines
  └─ Usage and audit metadata
```

### 3.1 角色

保持最小：

| 角色 | 范围 | 能力 |
|---|---|---|
| `platform_admin` | 整个平台 | 创建、暂停企业；默认不读取企业内容 |
| `org_admin` | 单个企业 | 管理员工、付款配置和托管预设 |
| `member` | 自己 | 登录终端、使用个人数据和已分配预设 |

当前不做复杂部门树和 team manager 角色。企业就是第一版管理边界。

### 3.2 企业付款

企业成员使用企业额度时，链路为：

```text
客户端 session
  -> Rakazo 模型网关
  -> 检查当前 organization membership
  -> 使用组织对应的 New API 账户/令牌
  -> New API 扣组织额度
```

企业员工看不到 New API 地址和令牌。

没有企业的个人账号继续使用自己的 New API 映射和额度。

当前版本不提供“同一账号在企业额度和个人额度之间切换”。账号属于企业时，模型调用默认走企业额度；退出企业后恢复个人额度。

## 4. 管理员面板

需要管理员面板，它是内部管理工具，不是员工端 Web 产品。

```text
https://admin.example.com
```

第一版只保留必要页面：

1. 组织列表和状态。
2. 员工邀请、禁用和移除。
3. 企业付款和额度状态。
4. Bot 模板、群预设、Knowledge、Skills、routines 的发布与分配。
5. 客户端版本、用量、错误和诊断上传请求。

不做：

- 复杂审批流。
- 多级部门管理。
- 可视化 bot 编排。
- 员工对话正文浏览。
- 远程控制员工电脑。

管理员需要独立登录、MFA 和操作审计。

## 5. 企业预设分发

管理员发布一次，组织内所有员工自动同步。

```text
管理员发布版本
  -> 分配给 Organization
  -> 员工客户端请求 Client Manifest
  -> 下载新增/变更包
  -> 校验签名和 hash
  -> 后台写入本地缓存
  -> 下一次 Agent run 使用
```

### 5.1 Manifest

```text
GET /v1/client/manifest
```

服务器根据 session 自动找到当前 organization 和成员权限，返回：

- bot 模板。
- group 预设。
- Knowledge 引用。
- Skills。
- routines。
- 功能策略。
- 最低客户端版本。

客户端不需要传 organizationId，也不能选择其他企业。

### 5.2 托管内容的用户体验

- 企业 bot 显示企业托管标识。
- 企业 preset 默认只读。
- 员工可以复制企业 bot 为自己的个人 bot 后编辑。
- 企业更新 preset 后静默生效。
- 管理员撤销分配后，客户端停止展示该托管内容。
- 用户自己创建的数据不会被撤销操作删除。

## 6. 功能放置

| 功能 | 服务器 | 客户端 | 说明 |
|---|---|---|---|
| 个人账号 | 权威 | session | Better Auth |
| 企业成员关系 | 权威 | 只读同步 | 单账号单企业 |
| 企业付款/额度 | 权威 | 只显示摘要 | New API |
| Bot 模板 | 权威版本 | 缓存和执行 | 企业托管 |
| 群预设 | 权威版本 | 缓存和执行 | 群消息仍在本地 |
| 群消息 | 不保存 | 权威 | 个人终端内 |
| `handoff_to_bot` | 不参与 | 执行 | 客户端本地 |
| Knowledge | 权威和索引 | 检索缓存 | 服务器检索 |
| Skills | 权威版本 | 缓存和执行 | 声明式包 |
| Routines | 定义和调度 | 执行和运行历史 | 客户端在线时运行 |
| 企业 Memory | 权威 | 检索结果 | 管理员维护 |
| Bot/用户私有 Memory | 不保存 | 权威 | 本地 |
| 工具详细日志 | 默认不保存 | 权威 | 本地 SQLite |
| Run/tool 元数据 | 汇总 | 上报 | 不含正文 |
| 私有附件 | 不保存 | 权威 | 本地 |
| 预置附件 | 对象存储 | 缓存 | 随 Knowledge/Skill 分发 |

## 7. Memory

### 企业 Memory

- 服务器保存和版本化。
- 由管理员维护。
- Agent 通过 `memory_search` 获取相关片段。
- 普通员工不能修改企业 Memory。
- Agent 可以提出晋升建议，但不能直接写入。

### Bot/用户私有 Memory

> 状态：个人版已实现，核实日期 2026-10-21。企业共享部分尚未实现。

- 客户端 SQLite 保存 `bot` 和账号级 `user` 文档，并保留完整 revision 历史。
- 默认不上传；bot 与共享文档可分别导出 Markdown。
- 直聊注入 32 KiB 上限的背景上下文；群聊不暴露私有 Memory 工具。
- 只有明确操作才晋升到企业 Memory。

## 8. Routines

> 状态：本地定义、调度和执行已实现，核实日期 2026-10-21。服务器定义与分发尚未实现。

服务器保存定义和调度规则：

- 所属企业。
- 目标 bot/preset。
- 触发时间。
- 启用状态。

客户端执行：

- 调模型。
- 使用本地工具和浏览器。
- 保存本地结果。
- 上报 run 元数据。

客户端离线时不执行本地任务。第一版策略固定为“下次启动补跑最近一次”，以后再做用户可配置的跳过/补跑策略。

当前本地版本每条 routine 只有一个 cron/一次性 schedule，并提供运行历史。watch、webhook、
GitHub 和消息平台触发不在当前实现内。

## 9. 工具日志和活动历史

详细日志默认留在客户端：

- runId、tool name。
- 参数和结果摘要。
- 审批、时间、耗时。
- 错误码和错误栈。
- 关联消息和本地文件。

服务器只记录：

- 企业、用户、设备。
- tool、status、error code、duration。
- token/usage。
- 配置版本。

需要日志排查时，客户端生成脱敏 diagnostic bundle，由员工主动上传或管理员发起请求后员工确认。服务器不默认上传 prompt、回复、命令输出、页面正文和附件。

## 10. 附件

- 员工私聊附件：本地。
- 企业管理端预置资料：服务器对象存储。
- 企业分发的 Knowledge 附件：服务器对象存储。
- 当前没有人类共享频道，所以不做团队共享附件。

> 本地个人附件已实现，核实日期 2026-10-21。预置附件和企业 Knowledge 附件尚未实现。

本地版本每条消息最多 4 个附件、单文件 10 MiB；文件正文存 SQLite。图片作为当前轮模型输入，
其他文件只发送名称/MIME/大小提示。详细附件内容默认不上传控制面。

中国部署优先使用国内 S3 兼容对象存储。

## 11. 管理和分发流程

```text
管理员编辑
  -> 发布版本
  -> 分配给 Organization
  -> 客户端后台同步
  -> 校验签名
  -> 本地缓存
  -> 立即或下次 run 生效
```

每种 package 都包含：

- id。
- kind。
- version。
- hash。
- signature。
- rollback version。

客户端保留一个已验证旧版本用于回滚。

> 客户端本地 Knowledge/Skills 已实现，核实日期 2026-10-21。`managed` 来源、package id
> 和 version 字段已落库，服务器签名 manifest 与分发尚未实现。

不允许从服务器下发未签名任意代码。Skills 第一版只包含 prompt、工具白名单、知识引用和声明式配置。

## 12. 明确不做

- Computer use。
- Voice 和电话。
- 海外第三方软件集成。
- Cloud Agent。
- 企业切换器。
- 多级部门树。
- 员工共享聊天频道。
- 团队共享电脑。
- 复杂管理员审批流。

## 13. 实施顺序

1. 服务器 organization、membership、企业付款映射和 tenant guard。
2. 最小管理员面板：组织、员工、发布和分配。
3. Client Manifest、签名包、客户端后台同步和回滚。
4. 企业 Bot 模板、群预设、Skills 和 Knowledge 分配。
5. 本地群聊和 `handoff_to_bot`。
6. Routines 服务器定义和分发；客户端定义、调度和执行已实现。
7. Memory 分层：个人本地 Memory 已实现；企业共享 Memory 和晋升流程待实现。
8. 工具运行记录、活动历史和诊断 bundle。
9. 私有附件、预置附件。
