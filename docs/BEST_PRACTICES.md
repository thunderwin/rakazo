# 使用最佳实践

> 核实日期 2026-10-20。本文基于当前代码，不基于官网文案。
>
> **适用范围：** 第 1–12 节描述上游服务器版 Rakazo 的现有行为。第 13 节说明 fork 的
> V1 桌面客户端目前具备哪些能力。官网宣传和代码不一致的地方集中列在第 14 节。

## 1. 规划 bot：一个 bot 只做一份工作

- **一个 bot 对应一个长期职责**（例如"收件箱"、"周报"、"竞品监控"），不要做万能 bot。
  每个 bot 只有一条连续的对话线程（`VISION.md`），职责混在一起会让历史、记忆和
  定时任务互相干扰。
- **创建后马上检查 instructions。** 创建时，description 会被原样复制成 instructions
  （`packages/contracts/src/domain.ts` 的 `normalizeCreateBotProfile`）。description
  是写给人看的简介，instructions 是写给模型的工作说明，两者应该分开写。
- **instructions 写清楚四件事**：职责范围、交付物放在哪里、什么情况必须先问、
  不该碰什么。上限 20,000 字。
- **模型和思考等级在创建后设置。** 创建表单不包含这两项。
- **bot 不能直接修改自己的 instructions。** `update_bot` 只能改名字、头像等资料。
  bot 想调整工作方式时，只能用 `propose_instructions_update` 提出修改，并且每次都要
  人工批准。instructions 保留最近 20 个历史版本，可以恢复。
- 新 bot 第一次运行只会复述它理解的职责，并询问需要什么。这次运行没有工具，
  用来确认 instructions 写得是否清楚。

## 2. 模型

- **每个 bot 可以用不同的模型。** 简单的整理、分类任务用便宜的模型，
  需要多步推理或操作网页的任务再用强模型。
- **需要操作屏幕，就选支持视觉的模型。** 不支持视觉时，桌面观察和操作工具会被
  直接移除，只剩页面文本工具和 shell。
- **配置备用模型。** 每个 Space 可以配置最多 10 个按顺序排列的备用模型。
  主模型不可用时会自动切换，并在对话里提示。注意：代码里的"Space backups"
  指的是这些备用模型，不是数据备份。
- **思考等级**：推理模型默认 `medium`，非推理模型默认 `off`。只对确实需要深度推理的
  bot 调高，高等级会明显增加耗时和费用。
- 单次输出默认上限 4,096 token，推理模型为 32,768。单个工具结果的文本会被截断到
  12,000 字。需要处理长内容时，让 bot 写进文件，再分段读取。

## 3. 记忆、草稿区和历史

| 工具                              | 作用                                   | 要点                                                |
| --------------------------------- | -------------------------------------- | --------------------------------------------------- |
| `remember`                        | 往这个 bot 的私有记忆**追加**一条事实  | 只记长期稳定的事实，比如偏好、约定、账号结构        |
| `save_shared_memory`              | 写入 Space 共享文档，所有 bot 都会读到 | **整份覆盖**，上限 4,000 字；只放全队都需要的事实   |
| 草稿区（scratchpad）              | 跨轮次的待办和搁置事项                 | 状态有 open / parked / done；不能当提醒或定时任务用 |
| `search_history` / `read_history` | 检索当前对话的历史                     | 每次最多 5 条；历史内容可能过时，按不可信数据处理   |

- **定期整理记忆。** 每次运行最多注入 32 KB 记忆。超出时，私有记忆保留**末尾**，
  共享记忆保留**开头**。所以共享文档要把最重要的内容写在最前面；私有记忆太长时，
  最早写入的事实会先被截掉。
- 记忆以"数据"而不是"指令"的身份注入。要改变 bot 的行为，修改 instructions，
  不要写进记忆。
- 配置了语义记忆服务（如 Honcho）后，`remember` 会被替换为 `save_memory`、
  `recall_memory` 和 `forget_memory`，其中删除操作需要审批。

## 4. 定时任务（routines）

- **prompt 必须写得能独立执行。** 定时任务运行时**看不到对话历史**，执行时需要的
  所有上下文都要写进 prompt 本身。
- **在 prompt 里点名要调用的插件工具。** 工具说明里明确建议优先用已连接的插件，
  不要用浏览器或网页搜索去获取应用里的数据。这样更快、更便宜，也更稳定。
- **一定要设置时区。** 默认时区是 UTC，不设置的话"每天早上 9 点"会按 UTC 执行。
- **错过的执行不会补跑。** 服务停机期间到期的任务，恢复后只执行一次，
  不会把错过的次数都补上。
- 最小间隔为 1 分钟；一次性任务的时间必须在未来。
- **变化触发（watch）只盯一个具体对象**，比如一个文件、一个命令或一个只读工具，
  不要盯整个账号。检查间隔最少 5 分钟，默认 15 分钟。命令类 watch 需要人工批准一次；
  会修改数据的工具不能拿来做 watch。
- 在定时任务的 prompt 里写 `@技能名`，执行时会自动展开成对应的技能。
- 定时任务运行时不能再创建新的定时任务，执行中也不能插话干预，但仍然可能弹出审批卡。

## 5. 技能

有两套机制，用途不同：

- **SKILL.md 技能（AgentSkill）**：同一 Space 内同一用户的所有 bot 共享，
  适合写可复用的通用流程。**不要在技能里写具体的账号名、频道或收件箱**，
  这些放在定时任务或 instructions 里。prompt 里最多列出 50 个技能；
  在输入框里输入 `/技能名` 可以强制使用某个技能。
- **示教技能（TaughtSkill）**：你在电脑上演示一遍，系统整理成这个 bot 专属的操作手册。
  需要图形界面的沙箱电脑，本机电脑模式不支持；每次录制默认 10 分钟内有效；
  开始录制会中断这个 bot 正在进行的运行。整理出的手册默认带一条审批边界：
  不经批准不发消息、不花钱、不发布、不删除。

## 6. 审批：先补上默认放行的高风险操作

- **默认不需要审批的操作包括 `shell`、`write_file` 和 `spawn_bot`**
  （`packages/core/src/action-approval.ts`）。在共享电脑或重要数据旁边工作的 bot，
  应该为这几个工具添加"需要审批"的规则。
- 默认就要审批的操作包括：生成图片和视频、写入外部目标、删除或归档 bot、
  删除记忆和密钥。
- 改变安全边界的操作（创建 Space、修改其他 bot 的 instructions、建群等）
  **只能逐次人工批准**，不能设置为永久允许，也不能交给自动审查。
- **打开两条内置规则**："对外发邮件前询问"和"购买前询问"。
- 插件工具的判断方式：只要工具名里有 send、create、delete、update、post、pay
  这类动词，或者工具自己声明会修改数据，就需要审批。
- 规则匹配时越具体越优先：具体工具 > 某个插件 > 某个类别。同一层级里有冲突时，
  "需要审批"胜出。
- **自动审查默认关闭。** 开启后，会用一个模型判断这次操作是否需要询问用户。
  它只会把操作升级为"询问"，从不静默拒绝；出错时按需要询问处理。
  每次判断都要额外调用一次模型，有费用。
- 审批卡不会阻塞对话，可以继续聊天，稍后再处理。

## 7. 密钥和账号

- **永远用 `request_secret` 弹出的加密卡片保存密钥，不要在聊天里粘贴。**
  模型没有任何读取密钥值的工具，由后端代为发送带鉴权的 HTTP 请求。
- **命令变量（command variable）会被 bot 的 shell 读到。** 只把愿意让这个 bot
  完全掌握的值存成命令变量；能用 HTTP 鉴权方式解决的，就不要用命令变量。
- 网站登录凭证只会被填进保存时指定的那个 HTTPS 域名。
- **遇到两步验证、验证码、通行密钥时，用 `request_takeover` 让人接手**，
  不要让 bot 索要验证码。
- 使用权限最小、可以撤销的 token。后端会过滤掉回显出来的密钥，但无法防范
  一个恶意服务故意变形后再泄露。
- 应用连接（Gmail、Slack 等）属于用户或 Space，不属于单个 bot。连接一次，
  多个 bot 都能用，所以授权范围要按"所有 bot 都会用到"来考虑。
- 手机端没有凭证管理页面，凭证的增删改要在 Web 或桌面端操作。

## 8. 电脑

- **团队电脑**：每个 Space 一台，所有 bot 共用文件和已安装的工具。每个 bot 默认在
  `bots/<bot-id>/` 目录下工作，需要共享的文件放 `shared/`。**这些目录不是安全边界**，
  任何团队 bot 都能读写整台电脑上的文件。
- **处理敏感数据的 bot 用私有电脑。** 文件、浏览器状态和工作数据都不能和其他 bot
  共享时，选私有电脑。
- **接管电脑前先停止 bot。** bot 正在运行时，团队电脑的接管请求会被拒绝；
  bot 主动请求接管（等待你输入敏感信息）的情况除外。
- **需要长期保留的软件，装在工作区里**，或者用 `uv tool install` 安装。
  装在系统目录的软件包在更换电脑供应商时会丢失。
- 默认空闲 10 分钟后关闭电脑，单台电脑最长连续运行 2 小时，单条命令最长 5 分钟。
  长任务要拆成多步，或者放到后台执行。
- 工作区在运行结束、停止和进入空闲前会做快照，但**只保留最新一份**，
  不是带历史版本的备份。

## 9. 多个 bot 协作

- **先把单个 bot 用顺，再加第二个。** 多个 bot 之间只能通过工具协作，
  一个 bot 在群里写"@某人"不会唤醒对方。
- 私下委托用 `message_bot`：对方完成后会自动把结果回传。单条消息上限 8,000 字；
  一条委托链最多传 6 跳，用户自己发的消息会重新从 0 开始计数。
- 群聊（2–10 个 bot）里用 `handoff_to_bot` 交接，不能直接交还给刚把任务交给你的 bot。
- **bot 管理能力（fleet）默认关闭，要逐个 bot 单独开启，并且不会继承给子 bot。**
  只有用户亲自发起的运行才能使用这些工具；运行中途收到聊天软件或 webhook
  的消息后，本次运行内就不能再做管理操作。bot 只能修改自己创建的 bot，
  不能删除 bot，不能动密钥。
- 任务需要多个 bot 长期接力时，用工单看板。由工单唤醒的运行不能给用户或
  其他 bot 发消息，只能通过工单评论汇报进度。
- 只是临时帮手，不需要长期身份时，用 `run_subagent`，不要创建新 bot。

## 10. 接入聊天软件

- Slack、Telegram、WhatsApp、iMessage、飞书都是可选接入，配置好对应的凭证后才会启用。
- 每个 bot 只能绑定一个聊天身份。
- 团队群聊的旁听模式（ambient）默认关闭。开启后，系统会把群消息攒 15 秒，
  再用一个模型判断要不要回应。这会产生额外费用，规则文字上限 4,000 字。
- 其他 bot 发来的消息默认忽略，可以按发送者改成"汇总"或"处理"。
- 从聊天软件触发的运行没有记忆、草稿区和工单工具。需要这些能力的工作，
  让 bot 回到它自己的对话里完成。

## 11. 成本控制

- **设置 `MAX_TOOL_CALLS_PER_TURN`。** 不设置或设为 0 时，单轮工具调用次数不受限制。
- **系统没有单次运行或单个 bot 的花费预算**，只记录用量。真正的额度控制在模型网关
  这一层（这个 fork 由 New API 负责）。
- 保持 instructions 和技能稳定。系统提示词把稳定内容放在前面，方便命中 prompt 缓存；
  频繁修改 instructions 会让缓存失效。
- 自动审查、群聊旁听判断、高思考等级、视觉截图都会增加调用次数或 token。
  按需开启。
- 能用插件工具或页面文本工具完成的事，就不要用截图操作。系统只保留最近 2 张截图，
  并会拒绝反复执行同一个没有效果的操作，但截图本身仍然是最贵的一种输入。

## 12. 备份、导出和删除

- **服务器运维**：用 `./scripts/backup.sh` 备份（PostgreSQL 导出加 `data/` 目录），
  生产环境用定时器执行，默认保留 3 份；恢复用 `./scripts/restore.sh`。
  `DATA_DIR` 要放在持久化、加密、并且有异地备份的磁盘上。
- **单个 bot 的导出**会生成一个 JSON 文件，包含资料、instructions、记忆、定时任务、
  工作区文件（隐藏文件除外）和完整历史。**目前没有导入功能**，导出文件只能用来存档或查看。
- 不再需要的 bot 优先**归档**，归档会保留对话、记忆和文件，之后可以恢复。
  删除 bot 时，可以选择是否同时删除它的记忆。

## 13. fork V1 桌面客户端的现状

V1 客户端在本机运行 Pi 循环。当前事实以 `docs/V1.md` 第 12 节为准；这一节原先的
“尚无记忆、Routines、浏览器、工具记录或完整 UI”描述已过期并删除。

- 本地 SQLite 保存 bot、对话、群聊、Memory、Routines、artifacts、Knowledge、Skills、
  MCP server、Fleet 工作项和 run/tool activity。
- 浏览器扩展、应用启动、屏幕观察/操作、MCP、Skills 脚本和 Fleet 工具已接入本地
  runtime；群聊和持久 bot 委派保存在本机。
- 模型调用经过服务器网关；对话正文不保存到服务器。
- `shell` 和写操作需要审批，但当前还没有危险命令分级、只读命令白名单或统一的风险审批
  策略。审批疲劳仍是未解决的产品安全风险。
- 本机 runtime 没有 VM 级沙箱，且仍运行在 Electron 主进程。工具卡住或进程崩溃会影响
  整个客户端；独立 utility process 尚未实现。
- Routines 只在客户端进程运行期间调度。合上电脑或退出应用时不会执行“半夜任务”。
- 本地数据只存在这台设备上。产品级导出/恢复和数据库/备份加密尚未完成；在补齐之前，
  换机、重装或磁盘损坏存在数据丢失风险。

## 14. 宣传和代码的差异

| 说法                         | 实际情况                                                                                                            |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| "新 bot 会先采访你"          | 只有固定的欢迎流程（选择关注方向、推荐连接的应用），加一次没有工具的自我介绍运行，没有由模型主导的采访              |
| "定时任务是可读的 Markdown"  | 定时任务的 prompt 是普通字符串                                                                                      |
| "操作会记录到审计日志"       | 外部操作记录在 `ExternalEffect` 表里，但没有找到对应的审计日志界面                                                  |
| 团队 bot 的浏览器登录状态    | `docs/computer-runtime.md` 说每个 bot 的登录状态独立，`VISION.md` 说团队 bot 共享同一个浏览器身份，两份文档互相矛盾 |
| `Bot.selfUpdateInstructions` | 这个字段会被保存，但没有找到使用它的代码                                                                            |
